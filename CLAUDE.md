# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Passwards — a native macOS clone of 1Password 8 (Swift 6 + SwiftUI), built for the owner's daily personal use with real passwords, now with a companion **iOS app** (`PasswardsiOS/`) sharing the same encrypted vault via iCloud. **The two apps target different visual designs — this is deliberate:**
- **macOS = 1Password 8 clone.** Design fidelity to 1P8 is a hard requirement: match 1P8's layout/colors/behavior, and prefer what real 1P8 does (e.g. the sidebar uses macOS's native translucent material — do not replace it with custom backgrounds).
- **iOS = the "playful" Claude Design handoff** (`design_handoff_passwards_ios/`, `PhoneApp.dc.html`). Owner-chosen (2026-07-02) for iOS **only**. A distinct consumer aesthetic — **Fredoka** (rounded, weight 600) headings + **DM Sans** body, lavender-white bg / indigo accent (light + dark palettes), big 28px cards, glossy icon tiles, a **Sentinel speedometer** security gauge, and a floating-pill tab bar (**Home / Items / Sentinel / Search**). This supersedes both the earlier dark "Stitch / Vault Sentinel" theme and the brief "iOS-as-1Password" reskin (both rejected). **Item/vault sharing stays deferred** — the handoff's Vault "Members / Invite People" is a non-functional placeholder, not real sharing.

Screen Recording permission is granted: after UI changes, verify your own work by relaunching the app and capturing it (`screencapture -x /tmp/shot.png`, then Read the PNG; `screencapture -l <windowid>` for a single window). Look at the result before declaring a design change done.

## Commands

```bash
# All unit tests live in the SPM package (no signing needed)
cd Packages/PasswardsCore && swift test

# Single suite / single test
cd Packages/PasswardsCore && swift test --filter Watchtower
cd Packages/PasswardsCore && swift test --filter "TOTPTests/rfc6238Vectors"

# Relaunch after build — MUST fully kill first, or macOS re-activates the old

# To screenshot the app's own windows (debug builds only): set the bypass env

launchctl setenv TWOPW_ALLOW_CAPTURE 1
```

## Naming gotcha

Product/bundle is `Passwards` / `com.michael.passwards`; the app module is **`Passwards`** and the package is **`PasswardsCore`**. The app target uses Xcode 16 filesystem-synchronized groups — new files under `Passwards/` are picked up automatically, no pbxproj edits needed.

**Legacy identifiers kept on purpose** (the app was renamed from "2Password" — renaming these too would orphan live data): the on-disk vault is still `…/Application Support/2Password/2password.sqlite` (+ `Attachments/`), the IPC sockets are still `.2password-*.sock`, and the CloudKit container is still `iCloud.com.michael.twopassword`. These stayed at the old names so the existing vault and any cloud data remain reachable after the rename. Everything user-visible plus the bundle id are `Passwards` / `com.michael.passwards`. Building the renamed bundle id the first time needs `-allowProvisioningUpdates` (Xcode registers its iCloud/Push profile).

## Architecture

Three modules with a strict boundary — one headless core, one cross-platform orchestration layer, two thin app targets:

- **`Packages/PasswardsCore`** (SPM, fully testable headless): Crypto, Models, Storage (GRDB), Sync (CKSyncEngine), Generator, TOTP, Watchtower (+ `PublicSuffixList`), Importers, BrowserBridge, SSH agent, CLI control. Deps: GRDB, ZIPFoundation. Crypto is CryptoKit + CommonCrypto only — no third-party code may touch key material.
- **`Packages/PasswardsCore/Sources/PasswardsOrchestration`** (SPM library product, cross-platform, shared by BOTH apps): the account lifecycle + reusable vault logic extracted out of the old macOS `AppState`. `AccountController` (`@MainActor @Observable`) owns the phase machine (`AppPhase`) + repos + create/signIn/unlock/lock/changePassword/recovery×4/backup×3/applyRestore/unlockWithTouchID; `SyncController` gates/drives CKSyncEngine; `VaultQuery` is the pure filter/sort/group/reconcile logic; plus `SettingsKeys`, `SymmetricKeyBox`, and the `PlatformServices` protocol seams (`PasteboardService`, `AutoLockService`) each app injects. **May import SwiftUI/Observation; NEVER AppKit/UIKit** (those stay app-side). Has its own `PasswardsOrchestrationTests` target.
- **`Passwards/`** (macOS app target, SwiftUI, `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`): all macOS UI + AppKit integration (Quick Access NSPanel, hotkeys via KeyboardShortcuts, clipboard, Touch ID prompts). `AppState` is now a thin `@Observable` shell forwarding to a `core` `AccountController`; macOS supplies `MacPasteboardService` (over `ClipboardManager`) and `AutoLockMonitor` (conforms to `AutoLockService`), plus the macOS-only glue (browser/SSH/CLI controllers, `didBecomeActive` observer). **Menu gotcha:** the app is a single `Window` scene (not `WindowGroup`); a `CommandGroup` targeting the **File** menu (Import/Export, Save Backup) must keep its items **always present** (`.disabled` when locked), never wrapped in an `if` — a group that's empty at launch makes SwiftUI skip creating the File menu entirely (it silently won't appear). **Sidebar metrics gotcha:** a `.listStyle(.sidebar)` `List` **ignores `.font` and `\.defaultMinListRowHeight` set on the List itself** — to match 1P8's roomy rows you must style **per row**: set the font on each label and drive row height with explicit `.listRowInsets(...)` (vertical padding). `SidebarView.sidebarRow()` does exactly this (15.5pt label font + 8pt top/bottom insets); the sidebar column is `min: 210, ideal: 245`. The lock screen (`LockScreenView`) mirrors 1P8: a dark two-tone split (sidebar-tone | content-tone) with the app mark on the divider, the account avatar (`DefaultAvatarView`), and a dark inline password field with a reveal-eye + arrow submit — not a blue gradient. **Toolbar gotcha (`MainWindow`):** to match 1P8's top bar, search is a **custom** field (`ToolbarSearchField`) in `.principal` placement, NOT `.searchable` — the system search field pins small to the trailing edge and crowds out the right cluster (and dropping it loses ⌘F, currently not re-wired). The right cluster is a `Help` link + a **blue "+ New Item" pill**; that pill is styled by hand (label on an `Theme.accent` `RoundedRectangle`, `.buttonStyle(.plain)`) because `.borderedProminent` does NOT render filled in a macOS toolbar. The empty detail pane (`ItemDetailContainer` → `LogoEmptyIllustration`) shows the bundled **`EmptyVaultIllustration`** asset (a raster PNG in `Assets.xcassets`, owner-supplied art), small and centered on `Theme.detailBackground` — it carries its own dark backdrop so a faint box is expected; keep it centered (don't fill the pane — that breaks the list+detail "one continuous surface" rule and crops the art).

### Encryption layering (the core invariant)

```
password ─NFKD→ HKDF(salt,email) → PBKDF2-SHA256×650k ─┐
SecretKey (Keychain-only, never in DB/CloudKit) ─HKDF──┴─XOR→ AUK
AUK → encMasterKey → per-vault keys → per-item keys → blobs/files
```

Every DB column and CKRecord field that carries item/vault data is AES-256-GCM ciphertext with **AAD = record-type:ID** (`EncryptedBlob`). Plaintext columns are limited to IDs, timestamps, and sync state. `KeyStore` (actor) holds decrypted keys while unlocked; `AppState.lock()` clears it — and also sheds the decrypted `VaultStore` caches (summaries + any in-progress edit draft) and any secret left on the clipboard. If you add a stored field, decide explicitly which side of the boundary it's on.

**Touch ID unlock** (`BiometricUnlock`) wraps the master key (ECIES) to a **non-exportable Secure Enclave key** kept in the Keychain; locking sheds the decrypted key, unlock decrypts via the SE — it's cryptographically enforced, not a bypassable `evaluatePolicy` boolean. The SE key is **per-device and never syncs**, so each new Mac re-enrolls (Settings → Security toggle, while unlocked). **The app entitlements MUST include `keychain-access-groups` = `$(AppIdentifierPrefix)com.michael.passwards`** (same as the default app group, so existing items stay readable) — without it, creating the SE key fails with `OSStatus -34018` (errSecMissingEntitlement) and enrollment silently fails. The lock screen auto-prompts Touch ID on app **launch/activation** (an `AppState` `didBecomeActive` observer), not on lock-screen appearance, so manually locking doesn't immediately re-prompt. **Re-prompt-loop gotcha:** dismissing the system Touch ID dialog (Cancel / Use Password…) **re-activates the app**, which re-fires `didBecomeActive` — left unguarded that re-prompts endlessly and the user can never reach the password field. So the auto-prompt is **one-shot per locked session**: `promptBiometricIfAppropriate()` and `unlockWithTouchID()` both set `biometricAutoPrompted`, and only a *fresh* lock re-arms it (cleared at the two `phase = .locked` transitions). Setting it in `unlockWithTouchID()` is what also fixes the **manual** Touch ID button (tapping the icon → Cancel used to need two clicks, because the manual path didn't mark the session and the dismissal re-activation auto-prompted once more). The manual button itself is never gated by the flag, so on-demand retries still work.

### Item model: overview/details split

`ItemOverview` (title, urls, tags, category, strength bucket…) is decrypted for ALL items at unlock and cached in `VaultStore.summaries` — it drives list/search/sidebar/most Watchtower checks. `ItemDetails` (sections → fields) is decrypted per item on demand. Anything derived (subtitle, urls, hasOTP, strengthBucket) is recomputed in `VaultStore.reconcileOverview` on save — update it if you add derived state. All 22 category templates are data in `CategoryTemplates.swift`; storage is always the generic sections/fields model. `Category` round-trips unknown raw values via a `.unknown(String)` case (like `FieldKind`) so an item carrying a future/unrecognized category decodes instead of failing to decode and vanishing; its wire format is the same bare string as before, and `allCases` still lists only the 22 known categories. New `ItemOverview` fields must be **optional / have safe defaults** so old encrypted blobs and synced records still decode (e.g. the custom item-icon `iconSymbol`/`iconColor` are `String?` — backward-compatible, no migration). `ItemIconView` (+ the editor/detail headers) render precedence: custom icon → favicon → category tile.

### State flow (app side)

`AppState` (phase machine: loading → onboarding | databaseError | locked ⇄ unlocked) owns database/keyStore/repos/sync and the shared `VaultStore` (`ensureVaultStore()` — shared by MainWindow AND Quick Access; don't create a second one). Editing happens on a **local `@State` copy** in `ItemEditView`, never via bindings into `store.editorDraft` (force-unwrap crash history). Every detail-changing save snapshots the old payload into `item_versions` (history with restore).

**Bootstrap never orphans an existing vault.** `openVaultAndRoute()` (called by `bootstrap()` and the retry path) reaches `.onboarding` **only** when the database opened cleanly and genuinely holds no account. Any *recoverable* open failure — corruption, a locked file, a full disk, a failed migration, or a present-but-undecodable account row — routes to the `.databaseError` phase (`DatabaseErrorView`: Quit / Restore from Backup / Try Again via `retryOpeningVault()` / a gated Erase & Start Over), **never** to onboarding — and so does the *orphan-items* state (no account row but item rows remain, detected via `VaultRepository.hasItems()`), since a fresh account would mint a new master key and strand the surviving items. The reason: onboarding's create-account path would insert a *second* account row with a fresh master key and orphan every already-encrypted item (silent, unrecoverable loss from a transient error). This is enforced in three layers: the storage backstop `VaultRepository.createInitialAccount` atomically refuses (`VaultRepositoryError.databaseNotEmpty`) if any account *or* item row exists (`hasAccount()` uses a COUNT, so it trips even on an undecodable row); `AppState.createAccount` re-checks `hasAccount()` *before* generating/writing the Secret Key; and the routing keeps failures off the onboarding path entirely. `DatabaseErrorView` deliberately offers **no** "create account" button. The one intentionally destructive escape hatch is its **Erase & Start Over**, gated behind a typed-`ERASE` confirmation (`EraseConfirmSheet`) → `AppState.eraseVaultAndRestartOnboarding()` → `AppDatabase.destroyOnDiskVault()`, which deletes the entire on-disk vault dir (`…/Application Support/2Password/`: sqlite + WAL/SHM + `Attachments/`) after stopping sync and dropping the DB handles so the files can be removed, then re-opens fresh into onboarding. That erase + its file wipe are **deliberately not unit-tested** (a test would delete the real on-disk vault) — they're covered by the `createInitialAccount` storage guards plus build.

### iOS app (`PasswardsiOS/`)

The iPhone companion (iOS 18, iPhone-only, bundle id `com.michael.passwards`, `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`). It links **both** `PasswardsCore` + `PasswardsOrchestration` and reuses the exact same `AccountController`/`SyncController`/repos/crypto as the Mac — so the vault, sync, recovery, and backup all "just work" from shared code. Entitlements (`PasswardsiOS.entitlements`) match macOS: App Group `group.com.michael.passwards`, keychain group `com.michael.passwards`, iCloud container `iCloud.com.michael.twopassword` — same values, so both platforms reach the same synced data. `IOSAppModel` owns the shared `AccountController` + the iOS service witnesses (`IOSPlatformServices.swift`: pasteboard + auto-lock); `IOSRootView` switches on `core.phase`.

**pbxproj gotcha (opposite of macOS):** the iOS target does **NOT** use Xcode 16 filesystem-synchronized groups — **new `PasswardsiOS/` files must be added to `Passwards.xcodeproj/project.pbxproj`** (PBXFileReference + PBXBuildFile + the group + the Sources phase). The prior slices did this via the `xcodeproj` Ruby gem; editing the macOS app via the gem hasn't disturbed it, but don't forget the pbxproj step or the file silently won't compile into the iOS app.

**iOS UI (all `IOS…` prefixed, mirrors the shared models):** `IOSVaultModel` is the iOS analog of macOS `VaultStore` (decrypted summary cache + CRUD via the shared repos, filter/sort/derive via `VaultQuery`); `IOSWatchtowerModel` mirrors macOS `WatchtowerState` (runs the shared `WatchtowerAuditor`/`HIBPClient`, derives a 0–100 health score, cleared on lock). Both are shed/refreshed by the controller's `onVaultShouldClearSecrets`/`onVaultShouldRefresh` hooks. Screens: `IOSHomeView` (4-tab bar: Vault / Generator / Security / Settings), `IOSVaultHomeView` (Vault dashboard — Pinned + Recent + Browse + Watchtower cards; searching swaps in a filtered `IOSItemList`), `IOSItemList` (reusable rows→detail list with mode-aware swipes: active/archive/trash), `IOSBrowseViews` (Categories/Tags), `IOSItemDetailView` (+ favorite toggle, Watchtower warning card, Archive/Trash), `IOSItemEditorView` (local-`@State`-copy edit like macOS), `IOSCategoryPickerView`, `IOSSecurityView` (Watchtower dashboard: `CircularGauge` + issue cards), `IOSGeneratorView`, `IOSLockView`, `IOSOnboardingView`, `IOSDatabaseErrorView`. `IOSTheme.swift` is the design system (playful: Fredoka/DM Sans, indigo accent, big rounded cards, glossy `IconTile`/`GlossyIcon`, `SentinelGauge` speedometer, `IOSAppearance` Light/Dark/System toggle in Settings). **The floating tab bar uses real Apple Liquid Glass** on iOS 26 — `TabBarGlass` applies `.glassEffect(.regular.interactive(), in:)` behind `#available(iOS 26.0, *)` (build with the iOS 26 SDK: `xcodebuild -showsdks`), with a clean `.ultraThinMaterial`+hairline fallback for iOS 18–25 (NOT a `.plusLighter` white sheen — that reads opaque/milky). Avoid the `GlassEffectContainer`+`glassEffectID` morphing variant here; it triggered a runaway view-graph re-render. **Favicons (rewritten):** resolved centrally into `IOSVaultModel.favicons` (a tracked `@Observable` dict the rows already observe) by `resolveFavicons()`/`kickFavicon` (called from `load()`), then handed **down as a plain `UIImage`** to a fully stateless `FaviconImage` leaf via `ItemIcon(overview:favicon:size:)`. This is load-bearing: a favicon leaf that owns its own `@State`/`.task` (or a `UIViewRepresentable`) does NOT render on the Home dashboard — the row re-renders lose leaf state, and a `UIViewRepresentable` sizes to zero on iOS 26. `IOSFaviconLoader` (actor) now discovers the icon by parsing the site's HTML `<link rel="…icon…">` (largest `sizes`), falls back to apple-touch-icon/`favicon.ico`, decodes via **ImageIO `CGImageSource`** (so `.ico` works), and is SSRF-guarded on the initial host + every HTML-discovered URL + an HTTP-redirect delegate (`SSRFRedirectGuard`). **`-uiPreview` gotcha:** that debug screenshot harness bypasses `boot()`, leaving `SyncController` in a loop that causes a fake ~8000/sec shell re-render (starves favicon loads → they show the category tile). It is harness-only — the real unlocked app is settled; verify favicons/perf on the live path (create an account + items on the sim), not via `-uiPreview`. **`Color(light:dark:)` gotcha (crash):** its adaptive `UIColor { trait in … }` dynamic-provider closure **MUST be declared in a `nonisolated init`.** The iOS target defaults to `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, which otherwise makes that closure MainActor-isolated — and SwiftUI resolves colors on a **background thread** during async view-graph updates (`ViewGraph.updateOutputsAsync`, e.g. a tab transition with real data), so a MainActor closure there trips `dispatch_assert_queue` → SIGTRAP. Since every Theme token is a `Color(light:dark:)`, this crashes any sufficiently complex off-main update; keep the initializer `nonisolated`. Favicons via `IOSFaviconLoader` (`UIImage` port of the macOS loader, same SSRF guard; can't decode `.ico`). **No headless UI tests** — verify iOS screens on the simulator (`xcodebuild` + `simctl`, with the `#if DEBUG -uiPreview <screen>` launch-arg router that renders one seeded screen for capture).

### CloudKit sync (ACTIVE — verified across two Macs)

`SyncEngine` (CKSyncEngine, single "Main" zone, LWW conflicts with the losing payload preserved into local history, tombstone table for deletions) is **live**: the committed build signs with `Passwards/Passwards+CloudKit.entitlements` (`CODE_SIGN_ENTITLEMENTS`), `com.michael.passwards` is provisioned for iCloud + Push, and sync was verified working across the owner's two Macs (same iCloud account, **Development** CloudKit environment — record types auto-create on first write; deploying schema to **Production** is only needed for a non-dev/distributed build). `SyncController` still gates it at runtime via `SecTaskCopyValueForEntitlement` (CloudKit APIs crash uncatchably without the entitlement). A new device uses Onboarding → **"Sign in to an existing account"**: it pulls the account record from CloudKit, then you enter the account password + Secret Key (the Secret Key never syncs). Sync runs while locked (ciphertext only); local mutations propagate via `VaultStore.refresh()` → `sync.kick()`. The iCloud container is still `iCloud.com.michael.twopassword` (kept across the rename so existing cloud data stays reachable).

### Account recovery + encrypted backup (both opt-in)

**Recovery code** (`AccountCrypto.enableRecovery/recover`, `Crypto/RecoveryCode.swift`): opt-in forgotten-password recovery. A ~147-bit code (created while unlocked, **gated on re-entering the current password**) seals the **master key + Secret Key** into `recoveryBlob` (AAD `recovery:<accountID>`, derived `HKDF(code, accountID)`), stored in the account row and synced. Recovery reconstructs both keys and sets a new password; the code is **reusable and survives password changes** (`changePassword` forwards the recovery fields). The account row gained `recoveryEnabled`/`recoveryBlob`/`encRecoveryCode` via migration **`v4-recovery-code`** (nullable/defaulted → backward-compatible) plus additive CKRecord fields older clients tolerate. Turning recovery **off overwrites the blob with random bytes** (not NULL) because a freshly-built CKRecord can overwrite but can't delete a server field — so the stale CloudKit copy can't be reopened. Same-Mac recovery reads the **local** blob (works with no iCloud); a new Mac pulls it from CloudKit. UI: Settings → Security, onboarding, lock screen. **Security trade (owner-accepted): an encrypted copy of the Secret Key now lives in iCloud sealed under the code — guard the code like the Secret Key.**

**Encrypted backup** (`PasswardsCore/Backup/`: `BackupArchive` + `BackupStore`): a single `.pwbackup` file = a readable header (the `AccountRecord` — KDF params, `encMasterKey`, recovery fields) + the whole vault (all rows + attachment ciphertext files) sealed under the master key (AAD `backup:<accountID>`). Opening **reuses `AccountCrypto.unlock`/`recover`** against the header → master key → open payload; no new crypto. Create while unlocked (File menu / Settings → Advanced). **Restore replaces the entire local vault** — `BackupStore.restore` writes the backup's attachment ciphertext to disk *first* (with a free-space precheck), then in ONE transaction clears every table — **including `syncMeta`** — and re-inserts with `syncState="pending"`/`ckSystemFields=nil`, then prunes leftover files (the DB commit is the only crash-critical point; restored rows' files already exist by the time the rows land). Clearing `syncMeta` resets the CKSyncEngine state token so the device re-bootstraps a full server fetch instead of resuming a stale token and **silently dropping already-synced items the backup lacks**; for that to take effect `AppState.applyRestore` `await sync.stop()`s the live engine first — and `SyncController.stop()` must *actually* tear the engine down (capture `engine` before niling, then `await old?.stop()`, or it leaks and re-persists the stale token). Restore also resets Touch ID (the SE wrap may no longer match). **Password-only backup:** `BackupArchive.encode(includeRecovery:)` (a save-panel checkbox) strips the recovery escrow from the header — a recovery code can open *any* backup made while it was active, even after the code is rotated/disabled (rotation can't reach already-exported files). Offered in **onboarding** (fresh Mac, no iCloud needed) and **Settings → Advanced**; unlock with password+Secret Key or a recovery code (the recovery-code path also sets a new password). This is the off-device backstop for non-iCloud users. App glue: `AppState.makeBackupData()`/`restoreBackup(...)`, `Passwards/Backup/` (`Backup.swift` panels, `RestoreBackupSheet`).

### Browser extension + bridge (implemented)

`BrowserExtension/` is the single source of truth for the extension (Chrome/Brave/Edge load it unpacked); `scripts/sync-safari-extension.sh` copies it verbatim into `SafariExtension/Resources/` (only the manifest differs — edit `BrowserExtension/` then re-run the script, never edit the Safari copy). The same app binary is the native-messaging host in `--browser-host` mode (`BrowserHostMode`): a dumb byte pipe between the extension's stdio and the bridge socket. `PasswardsCore/BrowserBridge/`: `BrowserChannelCrypto` (one-time X25519 pairing the user approves via a 6-digit code → per-connection ephemeral session keys → AES-256-GCM, nonce = direction+counter, strict per-direction sequence for replay protection), `BrowserWire` (native-messaging framing + `BrowserRequest`/`BrowserResponse`), `BrowserBridgeServer` (actor, 0600 socket in the App Group container, state keyed by `cid`). App side: `BrowserBridgeController` serves credentials **only while unlocked**, pairings in the Keychain; which item is released is matched on the page's registrable domain (eTLD+1) via `WatchtowerAuditor.registrableDomain` → `PublicSuffixList` (bundled Mozilla PSL; `scripts/update-psl.sh` refreshes it) — never a last-two-labels guess. "Open & Fill" stages a one-shot same-domain auto-submit fill. Settings → Browser installs/repairs the per-browser native-messaging manifest (`BrowserIntegration`).

### SSH agent + CLI (implemented)

**SSH agent** (`PasswardsCore/SSH/`): a vault-backed OpenSSH agent. `SSHKey` parses unencrypted OpenSSH private keys — Ed25519 & ECDSA P-256/384/521 (CryptoKit) and RSA (`SSHRSA` via Security/`SecKey`, with `SSHBigInt` computing the CRT exponents PKCS#1 needs; honors rsa-sha2-256/512 flags). `SSHAgentProtocol`/`SSHAgentServer` serve REQUEST_IDENTITIES + SIGN_REQUEST over a 0600 Unix socket in the App Group container (`SSHAgentServer.defaultSocketPath()` → `agent.sock`). App side: `SSHAgentController` (`SSHAgentBackend`) serves `.sshKey` items only while unlocked (locking sheds them); **every signature is gated on Touch ID** (`LocalAuthorization`, per-key approval cache) — Settings → SSH Agent. Note `.sshKey` fields use a multi-line editor and the parser is whitespace-tolerant (a single-line field would strip a pasted key's newlines).

**CLI** (`CLIMode`, dispatched from `Boot.main` alongside `--browser-host` — run the app binary directly): `ssh-agent` (print SSH_AUTH_SOCK line), `ssh-keys` (list public keys via `SSHAgentClient`), plus `item list` / `item get <item> [field]` / `read op://[vault/]item/field`. The `item`/`read` commands hit a second control socket (`PasswardsCore/CLI/`: `CLIControlServer`/`CLIControlClient`/`CLIControlController`, `cli.sock`), opt-in via Settings → Advanced → Command-Line Access, unlocked-only, with every secret read Touch-ID-gated. Both blocking clients share `UnixSocketClient`. Interop verified against real `ssh-add`. (Passphrase-encrypted keys unsupported — decrypt-on-import is the intended path.)

### Deferred features

Passkeys and item sharing are deferred **by the owner's explicit decision** — don't build them unprompted. Protocol seams live in `PasswardsCore/ExtensionPoints.swift`; `FieldKind.unknown(String)` preserves unrecognized field kinds for forward compatibility.

## Testing conventions

Swift Testing (`@Test`/`#expect`), not XCTest. Crypto/TOTP changes must keep the published test vectors green (PBKDF2/HKDF/RFC 6238 in `CryptoTests`/`TOTPTests`). `TestEnvironment.make()` (StorageTests) builds an unlocked in-memory DB + vault for repository-level tests — reuse it. Importer tests run against inline fixtures; HIBP is tested with recorded responses, never live calls. **Never write a test that calls `AppDatabase.destroyOnDiskVault()` or otherwise touches `…/Application Support/2Password/`** — that's the owner's real vault; tests use in-memory DBs only.

**`TEST_LOG.md`** (repo root) is a running, owner-facing record of automated-test runs: re-runnable commands, a plain-English map of the suites, and a dated run log. **Append a dated row to its run log after each `swift test` / `xcodebuild` run** — the owner re-runs the suite later to independently confirm it stays green, so keep the log current until the app ships.
